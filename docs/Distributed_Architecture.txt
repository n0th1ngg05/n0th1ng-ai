Distributed Compute Architecture — Development Reference

The distributed architecture of n0th1ng AI follows a Master–Worker model where the Laptop (Master) owns all application state and orchestration, while one or more Workers act purely as execution nodes for computationally expensive tasks. Workers never own conversations, databases, memory, embeddings, RAG, or application state. They simply execute requests and return results.

Design Philosophy

The Master is always the single source of truth.

Everything related to user state remains on the laptop:

Conversation history
SQL database
Knowledge Base
Memory
Embeddings
RAG
Prompt building
Model routing
UI

Workers never know who the user is or what conversation is happening. They simply receive a job, execute it using local hardware, and return the output.

Because of this separation, workers are completely disposable. If a worker disappears, the Master automatically falls back to local execution.

Adding a New Distributed Tool

Every new heavy-compute tool should follow the same architecture.

Step 1

Keep all application logic on the Master.

Examples:

deciding when to call the tool
validating arguments
prompt construction
database access
conversation updates
Step 2

Move only execution to the Worker.

Examples:

AI inference
image generation
OCR
vision models
PDF parsing
research crawling
speech synthesis
Step 3

Create a worker gateway.

Example:

POST /vision

POST /ocr

POST /marker

POST /image

The gateway should:

receive payload
ensure runtime is running
execute locally
return JSON

Nothing more.

Step 4

Register the tool.

Worker registration advertises:

tools:

vision

ocr

marker

image_generation

The Master will now automatically discover that capability.

Step 5

Route through the cluster.

What Should Stay Local

Never distribute components that own application state.

Keep on the Master:

SQL
Conversation
Memory
Knowledge Base
Embeddings
RAG
Prompt Building
Model Routing
File Upload Pipeline

These are lightweight compared to AI inference and rely on centralized data.

What Should Be Distributed

Distribute components that primarily consume CPU, GPU, RAM, or network bandwidth without needing centralized state.

Examples:

Speech Runtime
Vision Models
OCR
Marker PDF
Layout Analysis
Internet Search
Research Queries
URL Reading
Image Generation
Large AI Models
Future YOLO Pipelines

These tasks are ideal because they are stateless: the Master sends input, the Worker computes, and the result is returned immediately.

Core Principle

Move computation, never ownership.

The Master should always own the application's state and decision-making. Workers should only perform isolated, resource-intensive computations and return results. This keeps the architecture modular, fault-tolerant, horizontally scalable, and ensures that adding a new distributed tool follows the same predictable pattern with minimal changes to the rest of the system.
